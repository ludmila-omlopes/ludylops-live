## Findings considered and rejected

So nobody re-audits these:

- **Boost/bet double-spend race** (`boostGameSuggestion`, `placeBet`): not a bug — the debit uses a `gte`-guarded update with `.returning()` inside a transaction; zero-row → throw → rollback. This is the *correct* pattern (and the exemplar plans 004/005 copy).
- **HMAC verified over raw body then `JSON.parse` of the same string**: that is the textbook-correct order of operations, not a vulnerability.
- **CSRF on admin GET routes**: CSRF cannot read responses; the GETs require an admin session. No exploit path evidenced.
- **5-minute HMAC replay window** (`src/lib/streamerbot/security.ts:3`): industry-standard tolerance (Stripe uses the same); not worth tightening given Streamer.bot clock skew risk.
- **IDOR on `/api/viewers/[youtubeChannelId]`**: the DB path selects only public profile + balance fields, and balances are public by design (ranking page). Demo path returns demo data only.
- **Demo-store `structuredClone` cost**: demo mode only; negligible.
- **OBS overlay polling → serverless/Neon cost**: real but architectural (SSE/WebSocket redesign); deferred — revisit if Neon/Vercel bills climb.
- **`repository.ts` decomposition (10,033-line god module, duplicated demo/DB paths)**: real and HIGH-impact, but deliberately not planned this round — user selected the top-5 + hardening batch. Decompose only after 003/004/005 land (tests first). Re-raise next run.
- **Unbounded admin queries / O(n×m) suggestion assembly**: real, MED impact; not selected this round. Re-raise next run.
- **Beta email gating for creator-area creation** (requested 2026-07-07): already fully implemented — `canCreateCreatorArea` in `src/lib/creators/access.ts` (admin emails + admin-managed allowlist), enforced on the `/criar-area` page and on `GET/POST /api/me/creator-area`, with admin UI (`admin-creator-area-access-panel.tsx`) and tests (`access.test.ts`). No plan needed; only the landing page (007) was missing.
